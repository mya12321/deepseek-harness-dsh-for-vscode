## 验收提示 / Verification notes（多窗口共享实例、断连 Retry、工作区 cwd，2026-10-21 修复）

- 验收要点（修复后）：① **单实例**——同环境开 4+ 个窗口同时启动，`ps`/任务管理器里每个环境只应有一个 `dsh/lib/bin.js --port …`，且端口是配置端口；状态栏除拥有者外显示 `reused`；启动期间不应出现端口+1 的第二个实例。共享实例重启（DSH: Restart Server）后仍停在配置端口，不漂移。并发窗口数量再多也只允许一个窗口进入 spawn；等待窗口会显示「等待另一个 VS Code 窗口完成 DSH 启动」，超过冷启动等待预算则给出**可重试**的 `SHARED_START_IN_PROGRESS`，而不是再起一个。② **Retry 有界**——模拟断连（暂停/杀死实例或让端口接 TCP 不回包）后点 Retry，最迟约 15s（单次 API 期限）内必然落到错误页或重连成功，不会无限停在「Connecting」；DSH 输出通道可看到 `DSH_API_TIMEOUT`。③ **cwd 正确**——窗口打开文件夹 A 后立即在冷启动期间切到 B：侧栏最终应绑定 B（状态栏 tooltip 的 workspace 为 B），子进程 pid 不变；在绑定失败页点 Retry 或再次切换活动编辑器应重新尝试绑定，而不是被 `sameRoot` 早退拦掉。回归：`test/unit/sharedLaunch.test.js`、`test/serverManager.test.js` 的围栏端口扫描/健康轮询抛错用例、`test/unit/dshWebAuth.test.js` 的期限与 caller abort 用例、`test/extension.test.js` 的「启动期间切换工作区后按新根绑定」。
  Verification points (post-fix): (1) **Single instance** — start 4+ windows of one environment simultaneously; `ps`/Task Manager must show exactly one `dsh/lib/bin.js --port …` per environment, on the configured port, with every non-owner reporting `reused`. No second instance on port+1 may appear during startup. A shared restart (DSH: Restart Server) must keep the configured port (no drift). Only one window may enter spawn; waiters show "Waiting for another VS Code window to finish starting DSH…" and, past the cold-start wait budget, surface a **retryable** `SHARED_START_IN_PROGRESS` instead of starting a duplicate. (2) **Bounded Retry** — simulate a disconnect (pause/kill the instance, or make the port accept TCP but never answer) and press Retry: it must settle to an error page or a successful reconnect within roughly 15s (the per-request deadline) instead of hanging on "Connecting" forever; the DSH output channel shows `DSH_API_TIMEOUT`. (3) **Correct cwd** — open folder A, then switch to B while the cold boot is still running: the sidebar must end up bound to B (status-bar tooltip reports workspace B) with the child pid unchanged; Retry on a binding-error page, or another active-editor change, must retry the bind instead of being short-circuited by `sameRoot`. Regression: `test/unit/sharedLaunch.test.js`, the fenced-port-scan/throwing-health-poll cases in `test/serverManager.test.js`, the deadline/abort cases in `test/unit/dshWebAuth.test.js`, and "binds to the workspace current after a slow server start" in `test/extension.test.js`.

## 验收提示 / Verification notes（WSL 窗口误用 Windows 承载的 DSH，2026-10-12 修复）

- 根因链（用户报告 `DSH session API business error: workspace/invalid-path`）：Remote-WSL 的扩展宿主由 `wsl.exe` 启动，**不读** shell rc，于是 PATH 里只有 WSL interop 追加的 Windows PATH——`which dsh` 命中 `/mnt/c/.../AppData/Local/pnpm/bin/dsh`，而 Linux 侧真实存在的 `~/.local/share/pnpm/global/v11/<hash>/node_modules/@deepseek-ai/dsh`（0.1.7-rc.2）没有被任何一层解析扫描（POSIX 候选层不枚举 pnpm 全局 store，因为它的目录名是内容哈希，静态猜不到）→ managed 解析报 `RUNTIME_NOT_INSTALLED` → `auto` 回落 command 模式 → pnpm 的 POSIX `sh` shim 会自己 `uname -a`，在 WSL2 上 `wslpath -w` 后用 `node.exe` 收尾（`~/.local/share/pnpm/bin` 里只有 shim、没有 `node`，所以必然落到 Windows node）→ DSH 成了**Windows 进程**（现场 pid 6443：`/proc/6443/comm` = `node.exe`、`/proc/6443/exe → /init`、`PGID == pid`）。本机 `.wslconfig` 是 `networkingMode=Mirrored`，该 Windows loopback 端口对 WSL 可见，因此它不仅能被探测到，还会被同环境其它窗口**收养为共享实例**（注册表里 owner `vscodePid=1075`，attachers 1218/6963）。该进程只认 Windows 路径（`win32.parse('/home/…').root === '\\'`），复放浏览器认证后 `workspace/create` 对 `/home/andy/...` 稳定回 `{"code":"workspace/invalid-path","message":"Workspace path is not fully qualified: '/home/andy/…'"}`；而这层服务器原文被 `assertServerResponse` 丢掉（只留 `error.code`），界面上只剩光秃秃的 code，无法据此判断原因。
  Root-cause chain (user report `DSH session API business error: workspace/invalid-path`): the Remote-WSL extension host is started by `wsl.exe` and does NOT source the shell rc, so its PATH holds only the Windows PATH WSL interop appends — `which dsh` hits `/mnt/c/.../AppData/Local/pnpm/bin/dsh` — while the Linux-side install that genuinely exists (`~/.local/share/pnpm/global/v11/<hash>/node_modules/@deepseek-ai/dsh`, 0.1.7-rc.2) was scanned by no layer (the POSIX candidate layer never enumerated the pnpm global store, whose directory names are content hashes no static guess can hit) → managed resolution answered `RUNTIME_NOT_INSTALLED` → `auto` fell back to command mode → pnpm's POSIX `sh` shim runs its own `uname -a`, `wslpath -w`s itself on WSL2 and ends in `node.exe` (`~/.local/share/pnpm/bin` holds shims and no `node`, so the Windows node is the only fallback) → the DSH became a WINDOWS process (live pid 6443: `/proc/6443/comm` = `node.exe`, `/proc/6443/exe → /init`, `PGID == pid`). With `networkingMode=Mirrored` in this machine's `.wslconfig` that Windows loopback port is visible from WSL, so the instance was not merely reachable — sibling windows of the same environment ADOPTED it as the shared instance (registry owner `vscodePid=1075`, attachers 1218/6963). Such a process only understands Windows paths (`win32.parse('/home/…').root === '\\'`), and replaying the browser auth flow showed `workspace/create` answering `{"code":"workspace/invalid-path","message":"Workspace path is not fully qualified: '/home/andy/…'"}` for every POSIX path — while `assertServerResponse` dropped that sentence (keeping only `error.code`), so the UI showed a bare code with no way to tell why.
- 验收要点（修复后）：① **解析**——用扩展宿主的真实 env/PATH 调 `resolveLocalDshRuntime`（不带 `manifestUrl`）必须得到 Linux 原生结果：`executablePath` 是 `~/.nvm/versions/node/<ver>/bin/node`、`entrypointArgs[0]` 是 `lib/bin.js`，全路径都不含 `/mnt/c`。② **端到端**——用**临时** DSH home 副本 + 备用端口启动该原生 dsh，复放浏览器认证（`GET /?token=…` 取签名 cookie → `POST /api`）后 `workspace/create`（本仓库路径）必须 `result.ok === true`，随后 `workspace/delete` 回滚并停掉临时进程；核对 `/proc/<pid>/comm` 不是 `.exe`。③ **拒绝**——注册表里 `runtimeEnvironment` 与当前窗口不同的实例不再被收养（`adoptRunningDsh` 在探测前即返回 null 并发 `selfheal`）；无字段的旧条目按 `/proc` 观测判定，观测不到（非 Linux、无权限、进程已退）一律**不判外来**，绝不因此回归收养。④ **顺延**——共享模式下端口被外来实例占用时，本窗口从其 +1 起找空闲端口启动自己的原生实例（`_lastSpawnPort` 是 per-manager，不会持续漂移），其余窗口经发现路径收养它。⑤ **清理边界**——只有「本窗口自己拥有的」外来条目会被停掉并注销；兄弟窗口拥有的绝不碰；死宿主条目仍交给既有的 `sweepDeadOwnerEntries`（不给它加外来逻辑，保住「绝不碰活宿主子进程」）。⑥ **用户侧生效**——当前 3081 上的外来实例会被判为外来而不再被收养；执行一次 **DSH: Restart Server**（或在任意窗口先启动原生实例）即可回到原生运行，侧栏绑定恢复；错误页在 `workspace/invalid-path` + 非 Windows 宿主时会直接给出这条指引。
  Verification points (post-fix): (1) RESOLUTION — calling `resolveLocalDshRuntime` with the extension host's real env/PATH (no `manifestUrl`) must yield a native Linux result: `executablePath` under `~/.nvm/versions/node/<ver>/bin/node`, `entrypointArgs[0]` the package's `lib/bin.js`, and no `/mnt/c` anywhere. (2) END TO END — start that native dsh from a TEMPORARY copy of the DSH home on a spare port, replay the browser auth flow (`GET /?token=…` for the signed cookie, then `POST /api`): `workspace/create` for this repository must answer `result.ok === true`; then roll back with `workspace/delete` and stop the temporary process, checking that `/proc/<pid>/comm` does not end in `.exe`.
